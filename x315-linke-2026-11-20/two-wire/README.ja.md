# two-wire: CH32X315 を 1 線から 2 線へ（2026-11-20）

WCH-LinkE（`FBC18F0680B0`、ファーム 2.23）→ CH32X315MCU6（UID `36a0abcd9eb5bc48`）。OEP の ESP32-P4X（`e8f60ae84dd7`）で
LinkE の側のピンから取った（SWIO = GPIO16 = LinkE の SWDIO、SWCLK = GPIO21）。50 MS/s の流し続け。LinkE への USB の命令は
`tools/run_raw.py`（wch-protocols の e165 の `rawcmd.py` を 1 つの USB セッションで送る）。読みは `tools/dec.py`
（WireSkein の rvswd と swio の読みを時刻順に並べる）。

## 分かったこと

1. **X315 を 2 線にする書き込み**（1 線で、続けて）: DMI `0x7E`（config_pre）← `0x5AA50401`、`0x7D`（config）← `0x5AA58403`。
   1 線へ戻すのは `0x7E` ← `0x5AA58401`、`0x7D` ← `0x5AA58403`。config_pre の bit 15 が 0 で 2 線、1 で 1 線
   （QingKe のマニュアルの表と逆）。2026-10-22 の V407 の実験（ch32rv `docs/data-requests/measured/oep-m030-v407-2026-10-22.md`）は
   config に `0x5AA58000` を書いていた。
2. **LinkE の命令**: `81 0d 02 ee 03` で 2 線のモード、`81 0d 02 ee 02` で 1 線のモード（応答 `82 0d 01 00`）。WCH-LinkUtility の
   「2 線」のプルダウン（McuCompilerDll.dll `McuCompiler_SetSDLineMode`: `81 0d 02 ee {02|03}`、失敗は `81 55 01 {01|02}`）。
   `ee 00` / `ee 01` は SDI print の有効 / 無効で、同じ命令の並び。命令そのものは線に何も出さない。LinkE のモードは USB の
   セッションをまたいで残る（LinkE の電源を切ったときは未確認）。
3. **接続（AttachChip、family `0xe6` で SetSpeed の後）の線**:
   - どちらのモードでも、最初に 2 線で応答のない 4 フレーム（NOP / W 0x10 / W 0x10 / R 0x11）。
   - 1 線のモード（`ee 02`）: 続けて 2 線で `0x7E` ← `0x5AA58401`、`0x7D` ← `0x5AA58403`（2 線の target を 1 線へ戻す）、
     約 100 ms 後に 1 線で `0x7E`/`0x7D` ← `0x5AA50400`（何も変えない）、`0x7C`（capabi `0x11538403`）と `0x7D`（`0x5AA58401`）を
     読み、1 線で接続を続ける。
   - 2 線のモード（`ee 03`）: 2 線で `0x7E`/`0x7D` ← `0x5AA50400` を書いて DMSTATUS を読む。target が 2 線なら答え、2 線で接続を
     続ける（`6_*`）。答えなければ 1 線に落ち、1 線で上の 2 線にする書き込みをしてから 2 線で続けることがある（`2_*` の 2 回目の
     接続）。1 線で始めてそのまま失敗（`81 55 01 01`）することもある（`2_*`・`3_*` の最初の接続）。どちらになるかは未確定。
4. ch32rv（0.32.3）は `ee 02` / `ee 03` を送らない。LinkE のモードが `ee 03` のままだと、ch32rv の `target info` は
   `target-no-response` で失敗した（各 USB セッションの最初の接続が失敗し、ch32rv は 1 回しか接続しないため）。

## 記録

| ファイル | USB の命令（1 セッション） | 線 |
|---|---|---|
| `1_ee03` | 情報、SetSpeed e6、接続、`ee 03`、接続、接続 | 3 回とも成功。USB の応答は `1_ee03.usb.jsonl` |
| `2_ee03_again` | 同じ（前のセッションの `ee 03` が残った LinkE） | 1 回目は失敗、2 回目に 1 線で 2 線へ切り替えて 2 線で成功、3 回目は最初から 2 線 |
| `3_session_start` | 情報、SetSpeed e6、接続、SetSpeed 01、接続 | 1 回目は失敗（1 線で halt まで）、2 回目は 1 線で成功 |
| `4_ee02` | 情報、SetSpeed e6、`ee 02`、接続、接続 | 2 回とも 1 線で成功 |
| `5_manual_then_ee02` | 接続、DmiOp W `0x7E` `0x5AA50401`、W `0x7D` `0x5AA58403`、（`ee 02` のまま）接続 | 接続の頭で 2 線から 1 線へ戻され、1 線で答えるが接続は失敗 |
| `6_manual_then_ee03` | `ee 02`、接続、上の 2 つの書き込み、`ee 03`、接続、接続 | 書き込みの後の 2 回の接続は、最初から 2 線で成功 |

X315 の電源は LinkE から来ている（uhubctl で LinkE のポート 3-3.4 の 2 を切ると、RAM の値が崩れる）。撮り終えた後、LinkE は
`ee 02` に戻した。

## 電源とリセット（追記）

| ファイル | 手順 | 線 |
|---|---|---|
| `7_power_cycle_then_default` | 2 線にしてから LinkE のポートの電源を入れ直し（X315 も）、そのまま接続 | LinkE は `ee 02` の動き（`ee 03` は LinkE の RAM だけ）。1 線で成功 |
| `8_power_cycle_then_ee03` | 2 線にしてから電源を入れ直し、`ee 03`、接続 | 2 線の問い合わせに答えない（X315 は 1 線で起きる）。1 線で 2 線にする書き込みをしてから 2 線で成功 |
| `9_ndmreset_unclear` | `ee 03` で接続（2 線）、DMCONTROL に ndmreset、`ee 03` で接続 | 再接続は最初から 2 線。ただ ndmreset の書き込みが線に見えず、リセットがかかったかは不明 |

- 切り替えは X315 にも LinkE にも保存されない。オプションバイトは撮る前と同じ。X315 は電源を入れると 1 線。
- X315 が 2 線のまま LinkE を `ee 02` にすると、ch32rv の接続は失敗した（LinkE の 2 線の「1 線へ戻す」書き込みでは戻らない
  ことがある）。電源の入れ直しで戻した。
- システムリセットと NRST で 2 線が残るかは未確定。

## 速さ（LinkE の速さ high、X315）

| | 1 線 | 2 線 |
|---|---|---|
| 線 | パルス幅 250 / 850 ns | SWCLK 約 472 kHz（周期 2.12 µs、`9_*` の clock_speeds） |
| DMI のフレームの間隔 | 約 46 µs | 約 125 µs |
| AttachChip | 約 112 ms | 約 120 ms |

2 線の速さは別の命令で決まるらしい（McuCompilerDll.dll `McuCompiler_SetTwolineLowSpeed`: `81 0c 02 <a> <b>`）。今回は送って
いない。データシート（§1.4.22）は「2 線はダウンロードの速度を上げる」と書くが、この設定のままでは 1 線より遅い。

## 次に測ること（X315 を OEP の P4X の治具に移した後）

1. OEP で LinkE と同じ切り替え（1 線で `0x7E` ← `0x5AA50401`、`0x7D` ← `0x5AA58403`、続けて rvswd）が通るか。
2. システムリセットと NRST の後も 2 線が残るか。
3. 2 線の速さを上げたときの速さ（1 線との比較）。`81 0c 02` の 2 線の速さの値も。
4. target のクロックを落としたときに、1 線と 2 線のそれぞれが通るか。
5. 1 線のとき、PA14 をスケッチの GPIO として使えるか（LinkE の SWCLK がつながったままでは判断できなかった）。
6. CPU から SDI の config を書けるか（RM に記載なし）。コアの起動時に設定するかの判断材料。
